# 加站自动化与体检（2026-10-01）

## 站点类型自动探测（`site_probe.py`）

### 判定特征（实测，无鉴权 GET，不消耗额度）

| 网站类型 | 判定特征 |
|---|---|
| **NewAPI** | `/api/status` 返回体含 `quota_per_unit` |
| **sub2api** | `/v1/sub2api/billing` 含 `rate_multiplier`，**或该路径返回 401** |
| official | 域名命中官方站列表（deepseek / openrouter / anthropic 等） |
| unknown | 都不命中 |

`401 也算命中` 的原理：它说明**路由存在**、只是要鉴权 —— 这就是 sub2api 的招牌。

### 两层探测

1. 先**无鉴权**探（免费、不消耗额度）
2. 失败再**带 key** 探（更准）：试 `/v1/usage`（sub2api）与 `/api/log/token`（NewAPI）

### ⚠️ base_url 带 `/v1` 后缀，探测路径会拼错（踩过）

必须先去后缀再拼探测路径：

```
strip_api_suffix("https://api.xxx.com/v1") → "https://api.xxx.com"
```

首次实测时忘了这步，**18 个站全判 unknown**。

### 实测识别率

18 个候选站 → **12 个自动判出**（7 NewAPI + 5 sub2api）。
判不出的 6 个不是失败，是本来就不是标准中转站
（自建服务 / 官方 API / 路径特殊）。

带 key 后：`littlecold`（NewAPI）与 `tryaigc`（sub2api）均判对。

### 人工优先原则

`sites.json` 里**显式写了 `kind` 的站不探测** —— 你说了算。
探测结果缓存在 `_probe_cache`，不会每轮都探。

## 极简配置（加站只填两行）

```json
{
  "base_url": "https://api.xxx.com/v1",
  "hermes_providers": ["custom:xxx"]
}
```

`kind` / `host` / `label` 全可省 —— 加载时自动补全（`load_sites()` 里的 `autoprobe`）。

**加完不用重启守护**，下一个 5 分钟周期自动带上。

### kind=unknown 怎么办

启动时会打印提示，按提示补一行 `kind` 即可 —— 这是**唯一**需要手动介入的情形。

## 体检（`site_health.py`）

```bash
python site_health.py          # 一屏看完
python site_health.py --json   # 机器可读
```

输出：站点清单与判定依据 / 库体积与增长外推 / 采集耗时余量 / 异常提示。

### 自动预警条件

| 条件 | 提示 |
|---|---|
| `kind == unknown` | 需在 sites.json 显式写 kind |
| `collect_state.last_ok == 0` | 上次采集失败 |
| 超过 2 小时无新流水 | 提示（可能只是没使用） |
| 库体积 > 500 MB | 考虑归档 |
| **采集耗时 > 守护周期 60%** | 建议改并发采集 |

### 规模参考（2026-10-01 实测）

```
2 站 / 2563 条 / 5.8 MB / 约 285 条天 / 2359 字节/条
外推：一年 233 MB ｜ 五年 1.1 GB
采集耗时：NewAPI 约 20s/站（1000 条窗口），sub2api 聚合站约 4s/站
```

存储不是瓶颈（五年才 1 GB）。**真会出问题的是采集耗时会线性增长** ——
站变多时撞 5 分钟周期上限。解法：改并发采集（现在是一个一个串行采）。

## ★ 新 key 来了怎么办（2026-10-02 定规）

**先判断「新 key 属于哪个账号」，再决定怎么做。分三种情况：**

### 情况 A：同账号的新 key（最常见）→ **什么都不用做**

站方 `/v1/usage` 返回的是**账号级**聚合，不是单 key。所以：

- 新 key 产生的用量，**自动包含在账号总额里**
- 只要有一个有效 key 能查到账号数据，新 key 的消费就在里面
- 多 key 采集彼此**幂等去重**，重复采不会重复计数

**验证方法**（一条命令）：

```
用新 key 查 /v1/usage，与现有 key 对比余额/用量
  ├─ 余额一致  → 同账号 → 不用配
  └─ 余额不同  → 不同账号 → 走情况 C
```

实测例：dsh 的 `custom:your-provider` 与 `-5` 余额分别是 19.4270 / 19.4263
（细微差异只是采集时间差）→ 同账号。

### 情况 B：另一个中转站 → 走「加新站点」（填两行，见上一节）

### 情况 C：新账号（如注册了第二个账号）→ 作为**独立站点**加 `sites.json`

⚠️ 判据是**账号**，不是**域名**。同一站可能有多个域名入口（api / api2 / api4），
那是同一账号，**不构成新站点**。

### 失效 key 要清掉

实测踩过：`custom:your-provider-3` 一直返回 **401 INVALID_API_KEY**，
但旧版采集器静默吞掉这个错误（见 `pitfalls.md` 的「静默失败」条），
**长期没人发现**。新版会报「不完整：1/3 key 失败」，看到就把失效 key 从
`sites.json` 的 `hermes_providers` 里删掉。

## ★ 采集完整性标记（2026-10-02 新增）

`collect_state` 表新增三列，供「差值补贴」等上层消费者判断可信度：

| 列 | 含义 |
|---|---|
| `complete` | 1 = 全部 key 成功（本轮可作**权威锚点**）；0 = 部分/全部失败 |
| `ok_keys` | 本轮成功的 key 数 |
| `total_keys` | 本轮应有的 key 数 |

判定规则：`complete = 1 if (total_keys and ok_keys == total_keys) else 0`。

**为什么需要它**：融合层要用站方值重置基准时，必须确认这轮采集是**真完整**，
而不是「某个 key 挂了但整站仍标记成功」——后者会让站方累计值短期偏低，
融合层误当完整锚点 → 把本地待确认增量错误清零 → key 恢复后显示突然补涨。

**部分失败的处理**：仍有数据就**入库不浪费**，但 `complete=0` 且 `last_msg`
写明失败原因，上层可据此拒绝重置基准。

## 监控对象的选择原则

**只监控常用站。** 2026-10-01 实测：接了 4 个站，其中 2 个（littlecold 8 条、
tryaigc 8 条）基本没用量，纯属噪音 → 用户决定移除，只留 示例站 + dshapi。

> 与其担心「加到 20 个站会不会乱」，不如先问「我为什么要监控 20 个站」。
> 加的时候克制，比任何技术方案都管用。

移除一个站要**同时删两处**：

1. `sites.json` 的站点条目 + `_probe_cache` 里对应键
2. `store.db` 的 `usage_flows` / `flow_sessions` / `site_accounts` / `collect_state`

删前把待删行导出备份（`memory-backups/<日期>/`）。
