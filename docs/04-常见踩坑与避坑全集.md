# 坑全集

## 0. ★ quota 换算系数是「站点自定义」的

NewAPI 默认 `QuotaPerUnit=500000`，但**每个站可不同**，换站必须重新校准：

```
系数 = 当日 quota 合计 ÷ (站方网页显示人民币 ÷ 汇率)
```

在 `sites.json` 用 `quota_per_cny` 配。详见 `billing-and-conversion.md`。

## 0.5. ★ 聚合行重复计数（2026-10-01 修）

dshapi 同一笔用量在库里会留多种行，是同一笔账的不同切面：

```
client:<uuid>          逐条流水（网页端）★最细，优先
sub2api-daily:<日期>   按日汇总（sk- key）
sub2api-model:<模型>   按模型汇总（sk- key，day 为空）
```

三者 token/cost 重叠 → 全表 `SUM(cost)` 会把同一笔钱算多次（实测翻 2~3 倍）。

代码中统一用 `NON_FLOW` 过滤常量：**有逐条数据那天只认逐条**，无逐条（断采旧日）
退回按日聚合，按模型行永不进总额。

## 0.7. 内部任务会污染命中率（智能审批 / 标题生成）

特征：输入 330~850、**输出恒为 3**、cache=0、`frt=-1000`（非流式）、耗时 1~2s。
占条数 14% 但只占花费 0.5%。它们天然无缓存 → **必须单列，不计入命中率**。

过滤条件：`out_tokens <= 10 AND cache_read = 0 AND total_prompt < 1500`

### ⚠️ 同类型站的审批特征可以差很多（2026-10-01 实测）

示例站（NewAPI）与 dsh（sub2api）的审批记录形态不同，**同一规则套不上**：

| 特征 | 示例站（规则命中） | dsh（规则漏掉） |
|---|---|---|
| 输出 token | **恒为 3** | **15~949**（不固定） |
| cache_read | **恒为 0** | **234**（固定小值） |
| 是否流式 | 流式 | **非流式** |
| 命中现有规则 | ✅ 395 条 | ❌ **0 条** |

→ 现有规则是**照 示例站 特征写的**，在 dsh 上命中 0 条。
**审批特征取决于「Hermes 用哪个模型发请求」，不是站点程序** —— 加站后要实测。

## 3. TLS 握手偶发超时

example.com 会随机卡死（3s~90s）。`http_get()` 已做阶梯超时+3次重试，别去掉。

## 4. Hermes 的 `billing_base_url` 有别名

同一 host 拆成 4 个 provider 别名（`custom:your-provider` / `-2` / `custom` / `auto`）
+ 2 种 URL 变体（尾斜杠）。**统计必须 `LIKE '%host%'`**，否则漏 31%。

## 5. Hermes 侧不是流水是快照

`session_model_usage` 是「会话×模型×任务」累计，`first_seen` / `last_seen`
是会话活动窗口（最长 71 小时）→ **无法精确归日**。

## 6. 窗口不对等会让总量对比毫无意义

站方只留近 1000 条，本地是全量历史。直接比总量得到 ±几百% 的**假差异**。
必须只在**共同日**上严格对比。

## 9. ⚠️⚠️ 采集静默失败（2026-10-02 修，曾长期隐藏真 bug）

### 现象

适配器在 HTTP 非 200 时直接 `return [], {}`（空结果、**不抛异常**）。
上层只有捕获到异常才计入 `errs`，于是：

```
HTTP 401 / 500 / TLS 失败
   → all_norms=[]   errs=[]
   → 「全部失败」分支不触发
   → 写入 last_ok=1, last_msg=ok      ← 骗人
```

### 实际后果（实测抓到）

`custom:api-dshapi-icu-3` 这个 key **长期 401 INVALID_API_KEY**，
但因为错误被静默吞掉，**从外观上一直显示采集成功**，无人发现。

更严重的应用场景：基于站方值的「差值补贴 / 融合显示」会把这种
「假成功」当成完整锚点 → 把本地待确认增量错误清零 → key 恢复后显示突然补涨。

### 修法

引入 `CollectError` 异常：所有非 200 、解析失败、业务错误一律抛出，
由 `run_site` 归类为失败。同时新增**完整性标记**：

```
collect_state.complete=1   全部 key 成功（可作权威锚点）
collect_state.complete=0   部分/全部失败（有数据也入库，但不作锚点）
collect_state.ok_keys / total_keys   成功/应有 的 key 数
```

`site_health.py` 会自动报「不完整：N/M key 失败 — <原因>」。

### 教训

**「返回空」不等于「没有数据」——「请求失败」必须与「窗口内无记录」区分开。**
静默吞错误会让 bug 隐藏很久（本次到修复时才发现）。

## 10. 启动脚本的“任一存活即跳过”漏洞（2026-10-02 修）

`hermes_autostart.ps1` 曾把 `poll_loop` 和 `panel.py` 放同一个查询里：

```powershell
$running = ... | Where-Object { $_.CommandLine -like "*poll_loop*" -or $_.CommandLine -like "*panel*" }
if ($running) { /* 两个都不补拉 */ }
```

→ 后果：**panel 活着但 poll_loop 崩了**，脚本输出 already running，
**采集器永远不恢复**（而采集器才是关键的那个）。

修法：两个进程**分别查询、分别补拉**，且分别输出启动结果：

```
proxy-monitor: launched poll_loop + panel     # 只拉了缺的
proxy-monitor: already running (poll + panel) # 两个都在
```

## 11. 对账口径差异不是 bug（2026-10-01 实测）

我们库按**逐条流水**统计，站方 `/v1/usage` 是**聚合计费口径**，两者天然不同：

```
我们库 567 条 / ¥0.741   vs   站方账号级 421 条 / ¥0.500
```

差异来源：逐条含审批等内部调用（聚合口径不按同样规则计数）+ 标价与实付口径差。
**不是数据丢失。**

> 用户 2026-10-01 判断：站方可能当天数据转移丢失，不用深究。
